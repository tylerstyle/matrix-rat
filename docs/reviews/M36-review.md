## Findings

### 1. [HIGH] `--from` & encryption shields: `from_user: true` trusts unverified devices, unconfirmed keys, unverified identities, and undecryptable events (and CLI `--from` ignores `sender_in_doubt`)
- **Where:** `src/agent/proto.rs:100-105`, `src/agent/mcp.rs:480-503`, `src/agent/client.rs:296-298`, `src/matrix/convert.rs:362, 455-470`, `src/matrix/agent.rs:549-557`, `README.md:681-684, 694-696`
- **Detail:**
  - `Msg::sender_in_doubt()` (`src/agent/proto.rs:100-105`) excludes only `"identity_changed"`, `"sender_mismatch"`, and `"not_encrypted"`.
  - Meanwhile, `convert::shield()` (`src/matrix/convert.rs:455-470`) calls `event.get_shield(false)` (lax mode) on `matrix-sdk-ui = "=0.19.1"`. Tracing the pinned SDK (`matrix-sdk-ui-0.19.1/src/timeline/event_item/mod.rs:408-458`, `matrix-sdk-common-0.19.1/src/deserialized_responses.rs:139-188`, `matrix-sdk-crypto-0.19.1/src/machine/mod.rs:3271-3305`):
    1. **`"unverified_device"` (`Code::UnknownDevice | Code::UnsignedDevice`):** Even after verifying `--from`'s cross-signing identity in the UI, if a compromised homeserver (or rogue device token on `--from`'s account) attaches an unsigned device (`UnsignedDevice`) or unknown/injected device (`UnknownDevice` — SDK comment notes *"could have been a temporary injected device"*), `shield()` emits `Shield::UnverifiedDevice` (`Shield::serious() == true` in `src/model.rs:342`). Yet `sender_in_doubt()` returns **`false`**, so `mcp` wakes `wait_for_message` and sets `"from_user": true` (intentionally tested in `src/agent/mcp/tests.rs:464-488` for `"from my other phone"`).
    2. **`"unconfirmed"` (`Code::AuthenticityNotGuaranteed`):** Mapped from `DeviceLinkProblem::InsecureSource`, which covers forwarded/backed-up room keys *and* `SenderData::UnknownDevice { owner_check_failed: true }` (device found, does not own the session; `sender_data_finder.rs:227-234`). `sender_in_doubt()` returns **`false`**, so unconfirmed/insecure-source events get `"from_user": true` and wake `wait_for_message`.
    3. **Never-verified user identity (`VerificationLevel::UnverifiedIdentity`):** Because `get_shield(false)` runs in lax mode (`convert.rs:458, 468`), if `--from`'s cross-signing identity was never verified by the bot account, `get_shield(false)` returns `TimelineEventShieldState::None` (`warning: None`). A compromised homeserver can impersonate `--from` cleanly with `"from_user": true` and no `"warning"`.
    4. **`UnableToDecrypt` (`kind: "undecryptable"`) and `Redacted` (`kind: "redacted"`):** `event.get_shield()` returns `None` for undecryptable items (`event_item/mod.rs:414-416`), and `convert.rs:362` clears `shield = None` on redacted events. Both therefore have `sender_in_doubt() == false` and get `"from_user": true` / wake `wait_for_message` when `sender == from` (their `body` is a fixed local string rather than attacker text, so the risk is spurious wakes / missing the real answer rather than prompt injection).
    5. **CLI `read --from` / `listen --from` (`src/agent/client.rs:296-298`):** `is_from` checks only `!message.own && message.sender == from`, not `!message.sender_in_doubt()`. Scripts using `matrix-rat listen --from @you:server` will receive `"not_encrypted"`, `"sender_mismatch"`, and `"identity_changed"` events on stdout unless they inspect `"warning"` themselves.
  - Because of (1)–(3), `README.md:694-696` (*"With `--from` only your account's messages are marked as yours; that is as good as your homeserver and, in an encrypted room, your device verification"*) overstates the guarantee compared to the 3 cases enumerated at `README.md:681-684`.
- **Fix / Decision needed:** Confirm the intended security boundary with the user:
  - If `--from` should resist homeserver device injection, exclude `"unverified_device"`, `"unconfirmed"`, and `kind == "undecryptable"` (and consider `"redacted"`) from `from_user: true` / `wakes`, or add an opt-in flag if unverified personal devices must be allowed; document clearly that `--from`'s cross-signing identity must be verified on the bot account first (since `get_shield(false)` omits `UnverifiedIdentity`).
  - Decide whether CLI `is_from` (`read --from` / `listen --from`) should also skip `sender_in_doubt()` or explicitly document that callers must check `"warning"`.

### 2. [MEDIUM] `mcp::wait_for_message`: cursor (`self.seen`) can move backwards, and a decrypted `sender_in_doubt` message leaves its `"undecryptable"` placeholder in `found`
- **Where:** `src/agent/mcp.rs:647-686`
- **Detail:** Two bugs live in the `listener.next()` loop (`mcp.rs:663-678`):
  1. **Cursor moves backwards on late decryption (`lines 648, 671-673, 683-685`):** Suppose `latest[start..]` holds an undecryptable message `$u` (`at("$u") >= start`), followed by a newer waking message `$n` (either already in `latest[start..]` after `$u`, or arriving via `listener.next()` during `grace` so `at("$n")` is `None` and `newest` becomes `Some("$n")`). When `$u`'s key arrives within `grace` (`10s`) and `listener.next()` emits the decrypted `$u`, line `671` checks `if at(&message.event_id).is_none_or(|at| at >= start)` — which evaluates to **`true`** both when `$u` was in `latest[start..]` (`at >= start`) and when `$u` arrived live (`at == None`) — and overwrites `newest = Some("$u")`! `self.set_seen(Anchor::After("$u"))` then moves the cursor *behind* `$n`, so the next `wait_for_message` replays `$n` (and everything after `$u`) as new.
  2. **Stale `"undecryptable"` survives `sender_in_doubt()` (`lines 653-678`):** When an undecryptable event `$u` from `--from` initially arrives, `get_shield(false)` returns `None`, so `wakes(&u)` is `true` and `$u` enters `found` (`settle = Some(now + grace)`). If the room key arrives within `grace` and decryption reveals `"sender_mismatch"` or `"identity_changed"` (making `wakes(&message)` `false`), line `666` executes `if !self.wakes(&message) { continue; }` *before* looking up `message.event_id` in `found` (`line 674`). The stale `"kind": "undecryptable"` entry stays in `found`, holds out the full `grace` window, and is handed back with `"from_user": true` even though the decrypted event failed verification.
- **Fix:**
  - When `!self.wakes(&message)` arrives on `listener.next()`, remove any matching `message.event_id` from `found` (and recalculate `newest` if it pointed to that event) before `continue`.
  - Advance `newest` only for newly appended unseen live events (`None => { newest = ...; found.push(...) }`), never overwriting `newest` backwards when updating an existing entry (`Some(known)`) in `found`.

### 3. [LOW] Startup `SIGUSR1` race window between `ProfileLock::acquire` and `Signals::new()`
- **Where:** `src/main.rs:222-231`, `src/lock.rs:49-60`, `src/watch.rs:110-160`, `src/agent/serve.rs:1146, 1166`
- **Detail:** `main()` acquires `ProfileLock::acquire(&paths)` at `src/main.rs:222` — writing and locking `<runtime_dir>/<profile>.pid` — before `logging::init`, Tokio runtime creation, and `agent::serve::run` calling `Signals::new()` (`serve.rs:1166`) to register `SignalKind::user_defined1()`. If `matrix-rat --reload-theme` (`watch::signal_running_instances`, which validates the PID file lock and `/proc/<pid>/comm == "matrix-rat"`) runs in that startup window, Linux's default `SIGUSR1` disposition terminates `serve` before the socket is opened.
- **Fix:** Register/ignore `SIGUSR1` early in `main()` before `ProfileLock::acquire` (or block/handle `SIGUSR1` before writing the PID file).

### 4. [LOW] `clean_line(..., MAX_NAME = 256)` appends `'…'` to protocol identifiers (`RoomInfo.id`, `Msg.event_id`, `Msg.sender`)
- **Where:** `src/agent/proto.rs:44, 347-353`, `src/agent/serve.rs:495`, `src/matrix/agent.rs:507-508`
- **Detail:** Applying `clean_line(..., 256)` truncates at 256 Unicode chars and appends `'…'`. If an ID exceeds 256 chars, `RoomInfo.id` becomes unparseable by `RoomId::parse` in `joined_room` (`src/matrix/agent.rs:344`), and a truncated `Msg.sender` breaks `sender == from` matching.
- **Fix:** Strip control characters without appending `'…'` on machine identifiers (`id`, `event_id`, `sender`), reserving char-count ellipsis truncation for display fields (`RoomInfo.name`, `Msg.sender_name`).

### 5. [LOW] `Served` lacks `Drop`, and `NeedLogin` shutdown aborts `accept` before flushing `Stopping` replies
- **Where:** `src/agent/serve.rs:1036-1121, 1194-1198`
- **Detail:**
  - `Served` does not implement `Drop`: dropping it without `.stop().await` removes the socket file (`SocketFile::drop`) while leaving `accept` and `hub` running detached until the Tokio runtime shuts down.
  - On runtime `NeedLogin` / `NeedReauth` (`serve.rs:420-426`), `hub` posts `Code::Stopping` into pending `oneshot` / `News::End` channels and returns `End::NeedLogin`. `serve::run` immediately exits `select!` (`1195`) and runs `served.stop().await` (`1198`), which executes `self.accept.abort()` right away and drops its `JoinSet` of active `connection`/`stream` tasks before they may be scheduled to flush `Code::Stopping` onto their Unix streams — causing connected clients to see raw EOF instead of `Code::Stopping` (as `serve/tests.rs:747` accepts).
- **Fix:** Add a best-effort `Drop` aborting `accept` and `hub`, and yield/grace-wait briefly (or close `listener` first and let existing `connection` tasks flush `Stopping` within a short bounded timeout) before aborting `connections`.

### 6. [LOW] Duplicate JSON-RPC `id` bypasses `MAX_CALLS` tracking in `mcp::run`, and `--room` name is not pinned across calls
- **Where:** `src/agent/mcp.rs:169-227, 535-615`, `src/agent/serve.rs:717-734`
- **Detail:**
  - In `mcp::run` (`mcp.rs:169-227`), `running` is a `HashMap<String, AbortHandle>` keyed by `id.to_string()`, and line `203` checks `running.len() >= MAX_CALLS` (`8`) instead of checking `calls.len()` (or rejecting duplicate active IDs). Concurrent `tools/call` calls sharing the same `"id"` overwrite the `AbortHandle` in `running` while all tasks remain alive in `calls: JoinSet`, and finishing the first task removes the active task's `AbortHandle` (`line 190`), breaking `notifications/cancelled`.
  - When `matrix-rat mcp --room R` is given a room *name* or `#alias` instead of `!roomid`, `mcp` stores raw `R` and re-resolves it on every `send_message`, `read_messages`, and `wait_for_message` call (`wait_for_message` pins `listener.room_id()` only for its paired `read`). Renaming/swapping room names on the server can redirect subsequent tool calls (though `README.md:696-697` already recommends `!roomid`). Also in `Hub::resolve` (`serve.rs:717-734`), an exact room `name` literally starting with `#` takes precedence over canonical `alias` `#...` without `Ambiguous`.
- **Fix:** Track `calls.len() >= MAX_CALLS` (and reject duplicate in-flight IDs or keep per-call entries cleanly); consider resolving and caching `!room_id` once in `mcp` after the first `serve` lookup succeeds.

## Hard-Look Checklist

### 1. Unix socket & peer checks (`src/agent/socket.rs`, `src/audio/temp.rs`, `src/agent/serve.rs`, `src/agent/client.rs`)
- **Mutual `SO_PEERCRED` check (fail-closed):** Both ends use `socket::peer_is_us(&stream)` (`src/agent/socket.rs:154-164`: `stream.peer_cred().is_ok_and(|peer| peer.uid() == libc::geteuid())`). `serve::accept` (`src/agent/serve.rs:1004-1007`) drops non-matching UIDs (including root unless `serve` is root) *before* acquiring the `connections` semaphore permit or reading/writing anything. `Conn::open` (`src/agent/client.rs:98-102`) verifies `peer_is_us` immediately after `UnixStream::connect` before sending a request (mitigating socket redirection if a directory ever pointed elsewhere).
- **Symlinks, permissions & stale socket cleanup:** `socket::bind` (`src/agent/socket.rs:87-118`) requires an absolute path `<= MAX_SOCKET_PATH (100)` bytes, validates/creates the parent folder via `crate::audio::private_dir(folder)` (`src/audio/temp.rs:95-117`: `symlink_metadata`, real directory, `meta.uid() == geteuid()`, forces `0o700`), removes dead sockets via `remove_stale` (`122-144`: `symlink_metadata` refuses symlinks/files/dirs with `BindError::InTheWay`, `UnixStream::connect` treats `Ok` as `BindError::InUse` and unlinks only on `ConnectionRefused`), sets `0o600` on the socket, and records `(dev, ino)` in `SocketFile` so `Drop` (`73-82`) only unlinks if `symlink_metadata` is still a socket with matching `(dev, ino)`. The microsecond between `UnixListener::bind` (`100`) and `set_permissions(0o600)` (`102`) is gated by the `0o700` parent folder and `peer_is_us` on `accept`.
- **Non-blocking TOCTOU notes:** Without `ProfileLock` (e.g. direct `socket::bind` calls or mismatched `XDG_DATA_HOME`), two concurrent `remove_stale` -> `bind` racers can unlink the winner's newly bound socket (`socket.rs:132-139`), and `remove_stale` does not check `meta.uid()`/`peer_is_us` on an active foreign socket (resulting in `BindError::InUse`, never hijacked by clients). Also `private_dir` (`src/audio/temp.rs:95-116`) does not inspect ancestor directories above `folder` or use `O_NOFOLLOW`/`fchmod`, which only matters if `$XDG_RUNTIME_DIR` points inside a shared writable directory like `/tmp`.

### 2. Hostile socket peers & hostile Matrix content (`proto.rs`, `serve.rs`, `matrix/agent.rs`, `text.rs`, `format.rs`)
- **Bounded line reader & slowloris immunity:** `LineReader` (`src/agent/proto.rs:469-554`) reads into fixed 4 KiB stack buffers (`let mut chunk = [0u8; 4096]`), refuses to read past `max` (`self.buffer.len() > self.max` -> `Read::TooLong`, bounding memory to `~max + 4096`: `64 KiB` on `serve`, `256 KiB` on clients, `1 MiB` on MCP), and anchors a hard whole-line deadline (`self.began`, `line = 10s` on `serve`) on the first byte plus an `idle = 120s` timeout between lines. Trickling 1 byte/sec cannot reset the deadline (`Read::Stalled`). `write_line` (`558-574`) bounds `write_all` + `flush` to `limits.write` (`10s`).
- **Concurrency & queue caps:** `accept` enforces `Semaphore::new(32)` (`connections`), rejecting surplus peers inline without waiting for reads (`serve.rs:1008-1018`); `Hub` caps `waiting` at `64` (`ready = 20s`), `sends + reads` at `64` (`answer = 120s`, matching `Agent`'s `MAX_TASKS = 64`), and `watched` at `16` (`sync = 30s`, matching `AGENT_MAX_WATCHED = 16`). Listener channels are bounded to `backlog = 64` and fed via `try_send` (`serve.rs:279-290`), dropping slow readers (`Code::TooSlow`) rather than blocking `Hub`. `Seen` caps deduplication history at `SEEN_MAX = 1000` per room (`194-222`). `Hub` performs zero awaits/locks in handlers.
- **Matrix content bounds & sanitization:** `convert::event_message` and `agent::messages` strip control characters and BiDi overrides (`unsafe_char` in `src/text.rs:50-57`), `bounded_body` caps `body` at `MAX_BODY = 32 KiB` (`truncated: true`), `READ_MAX = 100`, `WATCH_TAIL = 50`, and `MAX_ROOMS = 2000`. `open` (`30s`), `PAGE_TIMEOUT` (`20s`), `READ_PAGES` (`8`), and `READ_BUDGET` (`60s`) bound slow/empty pagination against a stalled homeserver (`src/matrix/agent.rs:47-58, 356-428`).
- **Non-blocking DoS/spoof notes:**
  - `accept`'s inline `200ms` write timeout on saturated connections (`serve.rs:1016`) and `TooLong`/`Stalled` awaiting `limits.write` (`10s`) before releasing `slot` (`serve.rs:882, 887`) are minor under the local same-UID threat model.
  - `Hub::answer` runs `format::message` synchronously on the single `Hub` task (`serve.rs:619`), where `tighten_spoilers` (`src/format.rs:428-441`) has an O(lines²) table-row scan on up to 16 KiB of `|-` lines; moving `format::message` off `Hub` (or into `Agent::send`) avoids delaying `Hub`.
  - `unsafe_char` (`src/text.rs:50-57`) leaves inline zero-width/filler characters (`U+200B`/`200C`/`200D`/`FEFF`) inside non-blank display names (`Msg.sender_name`); `Msg.sender` provides the un-spoofable MXID (subject to Finding 4).
  - `agent::messages` (`src/matrix/agent.rs:486-520`) formats all cached `TimelineItem`s before `drain(..skip)` slices to `limit`/`WATCH_TAIL`.

Commands arriving during `mod.rs`'s 5s retry sleep (`1527`) are dropped and resolved by `session_restarted()` once the restarted session emits `LoggedIn`.

### 7. `send` bypassing the send queue (`src/matrix/agent.rs:372-379`, `src/format.rs:227-229`)
- `send_text` runs `room.send(content)` directly under `SEND_TIMEOUT = 60s` (`OPEN` / `ANSWER` hierarchy `60s < 140s < 300s`). `SendMessageLikeEvent` creates one `TransactionId::new()` per call (`matrix-sdk-0.19.1/src/room/futures.rs:193`); within that call, `RequestConfig::default()` (`config/request.rs:86-98`, `http_client/native.rs:112-168`) retries HTTP 429/5xx (`Transient`) with the *same* `txn_id` (homeserver deduplicates) and does not retry `NetworkFailure` (`timeout: Some(30s)`).
- **Double-send vs silent loss:** `serve` never retries across calls and never drops a send silently (`Code::Failed` / `"timed out; the message may or may not have been sent"`). However, because no `txn_id` is exposed or reused across `send` calls, if `SEND_TIMEOUT` (`60s`), `30s` HTTP timeout, `Hub` `answer` timeout (`120s`), or session restart (`tasks.abort_all()`) hits after the homeserver committed the PUT, a caller retrying `send` creates a new `txn_id` and can post the message twice. Client socket disconnect mid-send leaves the already-spawned `Agent` task running while `Hub::tidy` drops the closed reply channel.
