### [MEDIUM] Room-key export reserve-then-write TOCTOU race and bare relative paths
- **Where:** `src/matrix/devices.rs:616-633, 645-694` (`reserve`, `still_ours`, `export_keys`) vs `matrix-sdk 0.19.1` `src/encryption/mod.rs:1765-1786` (`Encryption::export_room_keys`).
- **Issue:**
  1. `reserve()` creates the destination with `O_CREAT | O_EXCL` (`mode 0o600`), drops the `File` path check into `export_room_keys(path.clone(), ...)`, and checks `still_ours(&file, &path)` afterwards. Because `Encryption::export_room_keys` calls `std::fs::File::create(path)` inside `spawn_blocking`, there is a TOCTOU window between `reserve()` (`line 649`) and `File::create(path)` (`matrix-sdk` line 1780). In a shared or world-writable parent directory (such as `/tmp`), another local user can unlink `path` in that window and either:
     - replace `path` with a symlink so `File::create` truncates/overwrites the symlink target with encrypted key export bytes before `still_ours` runs; or
     - replace `path` with an attacker-owned file (e.g., `0o644` or `0o600`) so ciphertext lands in an attacker-controlled inode before `still_ours` sees the mismatch (and note `still_ours` also omits `there.nlink() == 1` and skips `remove_file` when `!ours`).
  2. `src/matrix/devices.rs:645-647` calls `std::fs::create_dir_all(parent)` whenever `path.parent()` is `Some(parent)`. For a bare relative filename with no `/` (e.g. `Path::new("keys.txt")`), `parent()` is `Some(Path::new(""))`, which causes `create_dir_all("")` to fail with `ENOENT`.
- **How to fix without changing `matrix-sdk`:**
  - Confirming SDK surface: `Encryption::export_room_keys` is indeed the only non-testing export method on `Client` (`olm_machine()` is `pub(crate)` in `matrix-sdk`, and while `encrypt_room_key_export` is public in `matrix-sdk-crypto`, `OlmMachine::store()` is gated behind `testing`).
  - Instead of pre-creating `path` and letting `File::create(path)` open it, create a private `0o700` temporary directory inside the target's parent directory (`DirBuilder` with `mode(0o700)`), have `export_room_keys` write `<staging>/keys.txt` inside that unshared directory, ensure `0o600` + `sync_all`, and publish atomically to `path` via `std::fs::hard_link(&staged, &path)` (or `renameat2(..., RENAME_NOREPLACE)` on Linux), then unlink `<staging>/keys.txt` and remove the staging directory. POSIX `hard_link` / `linkat(..., 0)` never follows symlinks at `path` and atomically fails with `AlreadyExists` if any entry (including a dangling symlink) exists there, removing both the symlink/overwrite window and any moment where `path` exists with unintended permissions or ownership. (Staging inside `parent` ensures the same filesystem; guard `if !parent.as_os_str().is_empty()` before `create_dir_all`.)

### [MEDIUM] Secret zeroisation gaps and silent passphrase trimming on paste
- **Where:** `src/lineedit.rs:76-82, 169-177, 254-255, 280-335`, `src/text.rs:14`, `src/app.rs:2536, 2549, 2565, 3391-3392`, `src/app/verify.rs:136`, `src/app/devices.rs:348`, `src/matrix/devices.rs:588-592`.
- **Verified baseline:** `zeroize 1.9.1` (`src/lib.rs:520-565`) zeroes `self.spare_capacity_mut()` before elements in `Vec::zeroize`, so `Drop for LineEdit` (`src/lineedit.rs:76-82`) does wipe `[0..capacity]` of `self.text` on drop, and `matrix-sdk 0.19.1` wraps passphrases in `zeroize::Zeroizing::new(passphrase.to_owned())` inside `export_room_keys` / `import_room_keys` (lines 1775, 1834).
- **Remaining gaps:**
  1. **Per-keystroke and paste heap copies (`src/lineedit.rs`, `src/text.rs`, `src/app.rs`):** `LineEdit::insert()` (`lines 254-255`) calls `sanitize_line(raw)` -> `sanitize()` (`src/text.rs:14`), allocating an unzeroized `text.to_owned()` + `.replace('\n', " ")` `String` on every keystroke and paste into a secret field. `LineEdit::paste()` (`lines 280-284`) allocates `raw.replace("\r\n", "\n").replace('\r', "\n")`, and `App::on_paste()` (`lines 3391-3392`) allocates `text.replace(...)` unzeroized before forwarding slices (in addition to `crossterm::event::Event::Paste(String)` itself).
  2. **Pasting silently trims passphrases (`src/app.rs:3392`):** `let first_line = text.lines().next().unwrap_or("").trim();` strips leading and trailing spaces from pasted passwords/passphrases, whereas keyboard typing and `check_passphrase` preserve spaces.
  3. **Recovery key & login/setup secrets still use plain `String`:** `KeysPopup` opens `Modal::Recovery` via `Click::RecoveryKey` (`src/app/devices.rs:348`), yet `submit_recovery` (`src/app.rs:2565`), `submit_login` (`src/app.rs:2536, 2549`), and `submit_set_up` (`src/app/verify.rs:136`) extract and send unzeroized `String` into `MatrixCmd::Recover`, `MatrixCmd::LoginPassword`, `MatrixCmd::ReauthPassword`, and `VerifyCmd::SetUp` (`src/matrix/mod.rs:1346`, `src/matrix/verify.rs:793`). Only `DevicesCmd` (`SignOut`, `ExportKeys`, `ImportKeys`) uses `Zeroizing<String>`.
  4. **In-buffer lifetime and reallocation in `LineEdit` (`src/lineedit.rs:169-177, 286-335`):** `clear()`, `backspace()`, `delete()`, `delete_word_left()`, and `kill_to_end()` leave erased bytes in `text`'s spare capacity until `Drop` (even while the modal stays open); `set("")` drops the `SECRET_ROOM = 256` reservation; and inputs exceeding 256 bytes reallocate `String` without zeroising the old allocation. (Additionally, `sign_out()` at `src/matrix/devices.rs:588-592` copies the password into Ruma's unzeroized `Password` `String` for HTTP JSON serialization, which is unavoidable with Ruma's current API.)

### [MEDIUM] Truthfulness issues in Sessions and Key Backup status UI
- **Where:** `src/matrix/devices.rs:444-447, 483-499`, `src/devices.rs:458-555`, `src/ui/devices.rs:280-295`, `src/ui/modal.rs:312-318`.
- **Sessions `"verified"` vs unverified own identity:**
  - `Device::is_cross_signed_by_owner()` (`matrix-sdk-crypto-0.19.1` `src/identities/device.rs:832-844`) only checks `identity.is_device_signed(self)` — it does not verify `own_identity.is_verified()` (`is_cross_signing_trusted` at lines 805-830 does).
  - When this device's own identity is unverified (`!list.vouched`), `src/ui/devices.rs:288-295` correctly shows the red caveat `"This device is not verified itself, so it cannot check the others: “verified” below is what the server says."`, **but lines 280-286 still render green (`Role::StatusOk`) `"All N sessions are verified."` right above it** — including **`"All 0 sessions are verified."`** if `sessions` is empty after filtering dehydrated devices — and per-row `"verified"` labels stay green. (For comparison, `src/matrix/verify.rs:1402-1404` also uses `is_cross_signed_by_owner()` for `Security::device`.)
- **Key Backup `"backed up"` status (`src/devices.rs:458-555`, `src/matrix/devices.rs:483-499`):**
  1. `BackupState::Enabled` from `client.encryption().backups().state()` is local-only: on session restore (`resume_backup_from_stored_backup_key` in `matrix-sdk 0.19.1` `src/encryption/backups/mod.rs:930-948`), the SDK transitions to `Enabled` without contacting the server, and `Enabled` stays true even if keys have not finished uploading or failed to upload (`UploadState::Error`).
  2. `server_backup()` (`src/matrix/devices.rs:483-499`) reads `info.count` from `GET /room_keys/version` and discards `info.version`, so combining `BackupStatus::Enabled` with `ServerBackup::Present { keys }` can mix a local backup version with a different server backup version, or present `({keys} so far)` as complete coverage when local room keys have not uploaded.
  3. `backup_lines()` (`src/devices.rs:482-485`) emits `Tone::Good` `"Your message keys are backed up on the server."` even when `server == ServerBackup::Unknown` (initial state, offline, or `GET` error) whenever `BackupStatus::Enabled`.
  4. When local status is `Inactive`, `backup_lines()` (`src/devices.rs:492, 515-529`) sets `let exists = !matches!(server, ServerBackup::Missing);`, treating `ServerBackup::Unknown` as an existing server backup.
  5. In Settings (`src/ui/modal.rs:312-318`), `Setting::KeyBackup` colors every value other than `"on"` in `Role::Error` (red), including `"unknown"`, `"turning on…"`, `"downloading keys…"`, and `"turning off…"`.

### [MEDIUM] Repeated `/keys/query` every 30 s when a keyless device exists + watch lifecycle races
- **Where:** `src/matrix/devices.rs:228, 273-280, 372-443`, `src/app/devices.rs:70-80, 640-642`, `src/app.rs:3888`.
- **Issues:**
  1. **Continuous `/keys/query` loop:** In `list()` (`src/matrix/devices.rs:427-443`), `all_known` checks `response.devices.iter().all(|d| known.get(&d.device_id).is_some())`. If the account has *any* device in `/devices` with no E2EE keys (`SessionTrust::NoKeys`, e.g., a legacy web session, bridge, bot, or unencrypted client), `all_known` stays `false`, calling `encryption.request_user_identity(user_id)` (`matrix-sdk 0.19.1` `src/encryption/mod.rs:1401-1402`: `POST /keys/query`) on **every 30 s poll** (`POLL = 30s`) while either popup is open.
  2. **Shared poll loop & missing remote removal trigger:** Both Sessions and Key Backup trigger `DevicesCmd::Watch(true)` (`watch()` runs both `list` and `server_backup` every 30 s), and `watch()` (`line 402`) only handles `updates.new`/`updates.changed` for `user_id` — remote device removals wait up to 30 s unless triggered locally.
  3. **App watch lifecycle / stale data races:** `devices_watch()` clears `self.devices.list = None` on open, but leaves stale `self.devices.backup`; closing either popup leaves `on_tick()` (250 ms) to stop watching, so closing and reopening `< 250 ms` later keeps `watching == true`, skips clearing `list`, and skips `Watch(true)`; and `DevicesEvent::List` / `Backup` have no watch generation ID to discard stale in-flight events across close/reopen.

### [LOW] Key-request wakes (`KeyRequestWakes`) edge cases
- **Where:** `src/matrix/verify.rs:243, 250-351, 456-578`, `src/matrix/mod.rs:1463-1466`.
- **Flood safety assessment:** Well-bounded (`WAKE_SESSIONS = 512`, `UTD_FRESH_MS = 2 * 60 * 1000`, `WAKE_SETTLE = 20 s` after first `caught_up`, `WAKE_BURST = 2`, `WAKE_EVERY = 10 s`). Regardless of room traffic, backlog, reconnects, or FIFO eviction, outgoing wakes are capped at 2 immediate + 1 per 10 s (at most 8/min).
- **Small issues:**
  - `allow()` (`lines 309-318`) inserts `session` into `self.seen` *before* checking `!fresh || !settled || ration == 0`, so a fresh UTD arriving during the 20 s startup settle window or while rate-limited permanently consumes that session's nudge.
  - `send_queued` (`lines 462-484`) shares one `Arc<Notify>` with verification answers and unconditionally sends an `m.dummy` to-device `PUT` to our own device when woken — even if the SDK queued no key request (for instance when `devices.is_any_verified()` is false per `matrix-sdk-crypto` `src/gossiping/machine.rs:799-818` & `src/identities/device.rs:574-588`).
  - Comment at `line 459` says "only while one of our devices is verified", whereas `devices.is_any_verified()` specifically requires *another* verified device of ours; and `within()` (`line 243`) uses `abs_diff` (`±2 min`), allowing minor future clock skew.
