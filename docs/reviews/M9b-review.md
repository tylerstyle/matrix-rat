# Review: M9b — Room Management (join, direct chat, create, leave, invite, room info)

**Commit reviewed:** `610d4fe` (`Merge room management (join, direct chat, create, leave, invite, room info)`, verified against current `HEAD`)  
**Files inspected:** `src/manage.rs`, `src/app/rooms.rs`, `src/matrix/manage.rs`, `src/ui/roominfo.rs`, `src/action.rs`, `src/keymap.rs`, `src/palette.rs`, `src/app/palette.rs`, `src/modal.rs`, `src/app.rs`, `src/matrix/mod.rs`, `src/matrix/rooms.rs`, `src/ui/{mod,modal,sidebar,timeline,status,help}.rs`, `src/text.rs`, and snapshot diffs (plus pinned `ruma-common` `0.20.2`, `ruma-identifiers-validation` `0.14.0`, `matrix-sdk` `0.19.1`, `matrix-sdk-base` `0.19.1`).

---

## Summary

The feature architecture is well modularized (`src/manage.rs` holds pure popup/address logic, `src/app/rooms.rs` drives state transitions, `src/matrix/manage.rs` isolates SDK calls in the worker, and `src/ui/roominfo.rs` renders the modals and mouse hits). Room popups are pinned by `room_id` rather than sidebar vector index, Leave and Member Removal use double-step confirmation, server-side authorization is the source of truth (with failed changes triggering a `ManageCmd::Info` refresh), and hand-written `Debug` impls on `ManageCmd`, `ManageEvent`, `RoomDetails`, `NewPopup`, and `InfoPopup` redact private names, topics, aliases, and error strings.

However, there are several high-severity issues to fix before release: an input-triggered panic in `MatrixToUri::parse` on extra `/` segments, percent-encoded control/whitespace/Bidi smuggling in `parse_address` and `parse_user`, unsanitized `info.room_id` and pasted/typed modal text reaching the terminal raw, one-Enter / one-click irreversible DM room creation + invite from member rows, mismatched open-room vs sidebar-cursor targeting between the Command Palette / Timeline title click and `target_room()`, stale `ManageEvent` handling across logout/popups, heavy/error-blanking large-room member refreshes, and a `help_overlay` height overflow that pushes `Ctrl-Q Quit` off the help screen.

## Findings

### 1. [HIGH] Input-triggered panic in `MatrixToUri::parse` crashes the app on extra `/` segments
- **Where:** `src/manage.rs:65-68, 115-120` (calling `ruma-common-0.20.2/src/identifiers/matrix_uri.rs:49-83, 295-302`)
- **Detail:** `parse_address` (`src/manage.rs:65-68`) and `parse_user` (`src/manage.rs:115-120`) pass untrimmed slash fragments directly to `MatrixToUri::parse(first)`. Inside `MatrixToUri::parse`, `"https://matrix.to/#/"` and at most one trailing `'/'` are stripped, and `MatrixId::parse_with_sigil` strips at most one leading/trailing `'/'`, checks `s.matches('/').count() > 1`, splits on `'/'`, and unconditionally indexes `first.as_bytes()[0]` / `second.as_bytes()[0]` without checking `.is_empty()`.
- **Impact:** Pasting or typing `"https://matrix.to/#/!room:host///"`, `"https://matrix.to/#///!room:host"`, or `"https://matrix.to/#////"` into Join, Direct Chat, or Invite panics out-of-bounds (`index out of bounds: the len is 0 but the index is 0`) and crashes the terminal client.
- **Recommendation:** Normalize repeated slashes or reject empty slash-separated path segments in `matrix.to` URLs before calling `MatrixToUri::parse`.

### 2. [HIGH] Percent-encoded controls/whitespace and Bidi/zero-width look-alikes bypass `parse_address` / `parse_user`
- **Where:** `src/manage.rs:35, 65-90, 109-160`; `ruma-identifiers-validation-0.14.0/src/{lib.rs:65-67, room_id.rs:6-15}`
- **Detail:**
  1. `parse_address` checks `input.chars().any(char::is_control)` at `src/manage.rs:35` **before** `MatrixToUri::parse` and `MatrixUri::parse` percent-decode `%XX` sequences. Furthermore, when `parse_user` receives a `https://` / `http://` / `matrix:` link (`src/manage.rs:115-120`), it returns `parse_address` output directly, bypassing `parse_user`'s own `is_whitespace() || is_control()` check (`lines 130-135`). Because Ruma's `room_id::validate` allows any byte except `NUL` (`'\0'`) and `localpart_is_backwards_compatible` only rejects `[':', '\0']`, inputs such as `"https://matrix.to/#/%23room%1b[31m:example.org"` or `"matrix:u/bob%0a:example.org"` return `Ok(...)` with decoded `\x1b`, `\n`, `\t`, or spaces inside `Address` / `UserId`.
  2. Even unencoded, `char::is_control()` / `char::is_whitespace()` in `parse_address`, `parse_user`, and `parse_alias_local` do not reject Unicode directional overrides (`\u{200e}`, `\u{200f}`, `\u{061c}`, `\u{202a}..=\u{202e}`, `\u{2066}..=\u{2069}`) or zero-width invisible characters (`\u{200b}..`), permitting look-alike/spoofed targets (e.g., `@bob\u{200b}:example.org`, `@bob\u{202e}evil:example.org`) and raw Bidi injection if echoed before UI sanitization (e.g. `"“{name}” is not a server name."` at `src/manage.rs:48, 86`).
- **Recommendation:** Validate decoded target IDs, user IDs, and `via` names **after** URI parsing, rejecting control chars, whitespace, directional overrides, and zero-width characters (consistent with `src/text.rs:35-42`, plus ZWSP/ZWNJ/ZWJ/BOM for identifier inputs).

### 3. [HIGH] Unsanitized `info.room_id` and pasted/typed modal text reach the terminal raw
- **Where:** `src/ui/roominfo.rs:404-410, 427-433, 509, 660-678`; `src/ui/modal.rs:113-131`; `src/app.rs:2233-2268`; `src/app/rooms.rs:214-217, 299-316, 342, 371-375`; `src/ui/status.rs:67-68`
- **Detail:**
  1. `draw_info` (`src/ui/roominfo.rs:404-410, 427-433`) renders `info.room_id.clone()` directly via `fact(...)` without `sanitize_line(...)`. Since `ruma::RoomId::validate` accepts any non-NUL characters in `!localpart`, a hostile room ID containing `\x1b` / C1 controls or Bidi overrides writes unsanitized control sequences into the terminal buffer (`summarize()` in `src/matrix/mod.rs:786` also keeps `room.room_id().to_string()` unsanitized).
  2. `App::on_paste` (`src/app.rs:2235-2236`) only normalizes `\r\n`/`\r` and takes `.lines().next()`, passing C0/C1 controls (`\x1b`, `\x07`), `\t`, and Bidi overrides straight into `on_manage_paste` (`src/app/rooms.rs:299-316`). `on_manage_paste`, `on_new_key` (`lines 214-217`), and `on_manage_key` (`lines 342, 371-375`) store raw characters into `NewPopup`, `info.editing`, and `info.filter`. These fields are rendered directly with `Span::raw(...)` (`src/ui/modal.rs:129`, `src/ui/roominfo.rs:509, 673`), and `Stage::Create` / `submit_edit` forward unsanitized `name`/`topic` strings to the homeserver. (Note: `text_from_the_network_cannot_reach_the_terminal_raw` only tests pressing `Enter` on a `\x1b` paste in `Stage::Join`, not rendering before `Enter` or other inputs.)
  3. Similarly, `ui::status::draw` (`src/ui/status.rs:67-68`) renders `app.toast` without `sanitize_line` (while `matrix/manage.rs` sanitizes its own error/name strings, `Action::AcceptInvite` / `DeclineInvite` failures via `src/matrix/rooms.rs:141-158` -> `MatrixEvent::ActionFailed` reach `show_toast` unsanitized).
- **Recommendation:** Strip control/Bidi characters at paste/key ingestion (`sanitize_line`) for single-line modal inputs, sanitize `info.room_id` and `app.toast` at render time, and sanitize outgoing `Create`/`SetName`/`SetTopic` payloads (or preserve newlines cleanly in a multi-line topic model without raw controls).

### 4. [HIGH] Starting a direct chat from a member row creates an encrypted room and sends an invite on ONE `Enter` or ONE click
- **Where:** `src/app/rooms.rs:360-363, 371-374, 430-436, 516-526`; `src/manage.rs:490-503`; `src/matrix/manage.rs:472-487`; `src/ui/roominfo.rs:365-366, 588-589, 756-760`
- **Detail:** Pressing `Enter` once on an `InfoRow::Member` (`src/app/rooms.rs:360-363`) or clicking its `" chat "` pill (`lines 430-436`) immediately emits `ManageCmd::DirectChat { user_id }`. When `client.get_dm_room(&user)` returns `None`, `direct_chat()` (`src/matrix/manage.rs:482-486`) immediately runs `client.create_dm(&user)` — creating a new encrypted `TrustedPrivateChat` room on the homeserver, mutating `m.direct` account data, and sending an invitation to that user (including users who are still `invited` in the current room).
  Unlike `Leave` and `Remove`, this has **no confirmation**. The hazard is worsened because typing any character in `RoomInfo` auto-selects the first matching `InfoRow::Member` (`src/manage.rs:498-500`), while the member-row border footer (`src/ui/roominfo.rs:365-366`) prints `"↑↓ select · type to filter · Esc close"` without mentioning `Enter` (only the bottom `status_text` shows `"Enter: direct chat"` when height ≥ 4 and nothing else overrides it).
- **Is it acceptable?** Opening an *existing* DM on one `Enter`/click is fine; **creating a brand-new room and sending a server invite on one `Enter` is too easy to trigger accidentally** (especially right after filtering members). At minimum, either require a second `Enter`/click when no DM exists yet (e.g. `"Start a direct chat with <name>? Enter again to create, Esc to stay"`), or explicitly state `"Enter: open/start chat"` in the footer and confirm creation of new DMs.

### 5. [HIGH] Command Palette and Timeline-title click evaluate the open room while execution targets `target_room()` (`cursor_room()`)
- **Where:** `src/app/rooms.rs:36-42, 86, 234, 439`; `src/app/palette.rs:35, 68, 127-129`; `src/palette.rs:440, 495-536`; `src/ui/roominfo.rs:39-46`; `src/ui/timeline.rs:524`; `src/app.rs:2386`
- **Detail:**
  1. `open_palette()` (`src/app/palette.rs:35, 68`) sets `ctx.in_invite` and `ctx.has_room` from `self.room()` (**the active/open room**), which `src/palette.rs:440, 495-536` uses to enable/label `"Invite someone to this room…"`, `"Favourite on/off for this room"`, `"Leave this room…"` / `"Decline this invitation…"`, and `Action::RoomInfo`. Yet executing any of those actions calls `perform_manage`, which resolves `self.target_room()` (`src/app/rooms.rs:36-42`: `self.cursor_room()` when `self.focus == Pane::Sidebar`).
     - When `focus == Pane::Sidebar` on an Invite while a joined room is open, the Palette labels `"Leave this room…"` and enables Invite/Favourite, then targets the Invite (or fails with `"Accept the invitation first"`).
     - Conversely, when an Invite is open and the sidebar cursor is on a joined room, the Palette shows `"Decline this invitation…"`, yet opens `RoomInfo` to **leave the joined room under the cursor**. (`Action::DeclineInvite` at `src/app.rs:1495` always operates on `self.room()`.)
     - When `focus == Pane::Sidebar` and the sidebar filter/space currently matches zero rooms (`cursor_room() == None`), Palette entries remain enabled because `has_room == true`, then fail with `"No room is open"` / `"No room to invite to"`.
  2. `ui::roominfo::title_hit` (`src/ui/roominfo.rs:39-46`, called from `src/ui/timeline.rs:524`) binds `HitId::Do(Action::RoomInfo)` to the **open room's name in the Timeline title** without switching focus. If `self.focus == Pane::Sidebar`, clicking `#OpenRoom` in the Timeline opens `RoomInfo` for the sidebar cursor room instead.
- **Recommendation:** Either compute `PaletteContext` (`in_invite`, `has_room`) from `target_room()` and include the target room's name in `"Leave …"` / `"Invite to …"`, or restrict Command Palette actions & Timeline-title click to the open room (`self.active`) while reserving `cursor_room()` strictly for `F4` pressed inside the Sidebar (and set `focus = Pane::Timeline` when clicking the Timeline title).

### 6. [HIGH] Late `ManageEvent` responses are not guarded by `logged_out` across session boundaries
- **Where:** `src/app.rs:1905` (diff vs `1816, 1885`); `src/app/rooms.rs:623-697`; `src/matrix/manage.rs:241-245`
- **Detail:** In `App::on_matrix`, `MatrixEvent::Rooms(_)` and `MatrixEvent::Spaces(_)` are dropped when `self.logged_out` is true, **but `MatrixEvent::Manage(event)` (`src/app.rs:1905`) has no `if self.logged_out` guard**. Meanwhile `Manager::stop()` (`src/matrix/manage.rs:241-245`) only aborts `self.watcher` — spawned `Join`/`DirectChat`/`Create`/`Leave`/`Invite`/`Kick`/edit tasks continue running after `Logout` or session expiry.
- **Impact:** An in-flight `ManageEvent::Opened(Ok(room_id))` from the prior session sets `self.manage.pending_open` while `Modal::Login` is visible (jumping to that room if the user logs back in within `OPEN_WITHIN = 60s`), and stale `Err` / `Left` / `Done` events pop toasts over Login or mutate a newly opened session's modal.
- **Recommendation:** Guard `MatrixEvent::Manage(_) if self.logged_out => {}` in `App::on_matrix`.

### 7. [MEDIUM] Untagged `ManageEvent` races across popups and live room/permission drift in `RoomInfo`
- **Where:** `src/app/rooms.rs:261-269, 291-294, 307-313, 470-496, 623-747`; `src/manage.rs:475-480, 507-523`; `src/matrix/manage.rs:599, 644`
- **Detail:**
  1. **Cross-popup `Opened` / `Done` mismatch:** `ManageCmd`/`ManageEvent` carry no request ID. `manage_escape` (`src/app/rooms.rs:263-268`) allows `Esc` while `NewPopup.busy.is_some()`, and `ManageEvent::Opened` (`lines 625-646`) clears `busy` on **either** `Modal::New` or `Modal::RoomInfo`. Cancelling a slow Join/Create and opening `RoomInfo` (while saving/removing) lets the earlier `Opened(Ok)` close `RoomInfo` and navigate away, or `Opened(Err)` clear `info.busy` and inject the join error. Likewise `on_change_done` (`line 726`) does not verify `change` matches the pending `RoomInfo` operation, and `on_manage_paste` / `manage_clear_input` on `RoomInfo` (`lines 291-294, 307-313`) are not gated on `info.busy.is_none()`.
  2. **Invite-accepted & leave/ban staleness:** `watch()` (`src/matrix/manage.rs:599`) evaluates `let joined = room.state() == RoomState::Joined;` once before its loop and only exits on `RoomState::Left` (`line 644`, missing `Banned`). `InfoPopup.kind` is never updated from `apply_rooms` or `set_details`. Accepting an invite while `RoomInfo` is open leaves the popup stuck showing only `Decline invitation`.
  3. **Stale `confirm` / invisible `editing` on `set_details`:** `InfoPopup::set_details()` (`src/manage.rs:507-523`) and `select()` (`lines 475-480`) do not clear `self.confirm` (`Confirm::Remove` remains in the status bar if that member leaves or loses removability) or clear `self.editing` if `can_rename`/`can_set_topic` becomes `false` (hiding the input box while `on_manage_key` stays in edit mode and `submit_edit` still submits).
  4. **Demo optimistic mutation & swallowed refresh errors:** `InfoRow::Favourite` and `InfoRow::Notify` mutate `details` before checking `self.manage(command)` (`src/app/rooms.rs:478-496`), leaving state mutated in `--demo` mode; and `ManageEvent::Info(Err(_))` (`line 692`) is silently dropped once `info.details.is_some()`.
- **Recommendation:** Tag requests with a monotonic ID (or ignore `Opened` inside `RoomInfo`), reconcile `RoomInfo` kind/closing when rooms change or leave/ban, clear `editing` when capability drops (and `confirm` when `set_details`/`select` changes target), and gate `Favourite`/`Notify` mutations or revert on `manage() == false`.

### 8. [MEDIUM] Large-room member refetch churn, Megolm key discards, and error-blanking on fetch failure
- **Where:** `src/matrix/manage.rs:24-25, 598-720`; `matrix-sdk-base-0.19.1/src/client.rs:979-989`
- **Detail:**
  1. **Reload/re-sort on every `RoomInfo` update:** `watch()` (`src/matrix/manage.rs:635-647`) calls `details(&room, false, false).await` -> `room.members_no_sync(JOIN | INVITE)` after a 300ms coalesce on **every** `subscribe_info()` change. In `matrix-sdk-base`, `RoomInfo` updates on every `notification_counts` and `latest_event_value` tick (every incoming message), so keeping Room Info open in an active large room repeatedly reads all members from SQLite, runs `sanitize_line` twice per member, allocates `to_lowercase()` strings on every comparison in `sort_by` (`lines 707-720`), and double-clones `RoomDetails`.
  2. **Unbounded `/members` fetch & Megolm key rotation:** There is no member cap (compare `MAX_COMPLETION_MEMBERS = 50_000` in `src/matrix/rooms.rs`) or fetch timeout, and `room.mark_members_missing()` (`src/matrix/manage.rs:624`) followed by `room.members(wanted)` invokes `receive_all_members()` (`matrix-sdk-base-0.19.1/src/client.rs:979-989`), which calls `olm.discard_room_key(room_id)` ("Rotating room key due to full member list reload"). `LARGE_ROOM_REFETCH` (`60s`) applies only when `joined > 1000` (`LARGE_ROOM`), so active rooms up to 1000 members with count skew or churn re-sync the entire member list and discard room keys on every `(joined, invited)` change; rooms `> 1000` whose fetch was deferred schedule no timer after 60s.
  3. **Fetch failures wipe displayed members without error:** When `room.members(wanted).await` returns `Err`, `details` (`lines 680-683`) substitutes `Vec::new()` and `watch` emits `Ok(current)` with `members = []` and `members_loading = false`, wiping any already-loaded member list silently and latching `gave_up = Some((joined, invited))` until counts change.
- **Recommendation:** Guard large rooms with a member cap/pagination or avoid `mark_members_missing()` unless membership actually failed to sync; precompute sort keys; skip UI member reloads when `(joined, invited, name, topic, alias, power_levels, encrypted, direct)` did not change; and surface fetch errors instead of replacing a cached member list with `[]`.

### 9. [MEDIUM] Address parsing edge cases (`http://matrix.to/`, empty localparts, malformed `!roomid`, `matrix:` authority/`action`, and `via` handling)
- **Where:** `src/manage.rs:30-160`; `src/matrix/manage.rs:437-468`; `ruma-common-0.20.2/src/identifiers/matrix_uri.rs:295-330, 474-501`
- **Detail:**
  - **`http://matrix.to/` and uppercase URLs match then unconditionally fail (`src/manage.rs:65-68`):** `lower.starts_with("http://matrix.to/")` and `"HTTPS://..."` enter the `matrix.to` branch, then unmodified `first` is passed to `MatrixToUri::parse`, which strictly requires lowercase `"https://matrix.to/#/"` (`matrix_uri.rs:295`). Links with `?via=` before `#/` or extra web query parameters also fail.
  - **Empty localparts & malformed `!roomid` accepted:** `#:matrix.org`, `@:example.org`, `parse_user(":example.org")`, `matrix:r/:example.org`, `!`, `!abc` (missing `:server`), and `!r:host#extra` all parse as valid (`ruma::room_id::validate` allows anything starting with `!` without `\0`).
  - **`matrix:` authority, fragment, & `?action=` ignored:** `matrix://evil.com:999/r/rust:matrix.org#frag` drops authority and fragment (`matrix_uri.rs:475-500`), and `parse_address` drops `link.action()`, accepting `?action=join` on user IDs or `?action=bogus`.
  - **Quadratic / un-deduplicated `via` & input size:** `link_via` deduplication (`src/manage.rs:97-101`) is $O(N^2)$ before `via.truncate(5)` (`src/matrix/manage.rs:464`), whereas trailing server words (`lines 43-50`) are **not** deduplicated (repeating one server 5 times crowds out later servers and resolved alias servers at `matrix/manage.rs:449-453`). Valid IDs containing `,` split at `src/manage.rs:39`. Also `join()` (`src/matrix/manage.rs:446, 466`) calls `client.resolve_room_alias` once manually and then `join_room_by_id_or_alias(&target, &via)` resolves the alias a second time inside `matrix-sdk`.
- **Recommendation:** Normalize `http://` / casing on `matrix.to`, reject empty localparts and `!roomid` lacking `:server`, enforce `via` dedup + bounded count in `parse_address`, bound input field lengths (`alias`, `topic`, `address`, `user`, `filter`), and pass `&RoomOrAliasId::from(&*room_id)` after `resolve_room_alias`.

### 10. [MEDIUM] Destructive Leave/Forget asymmetry, DM lookup gaps, public-room directory visibility, and `set_notify` raw errors
- **Where:** `src/matrix/manage.rs:472-541, 571-577, 684-688`; `src/app.rs:1495-1504`; `src/ui/roominfo.rs:585`; `matrix-sdk-0.19.1/src/{client/mod.rs:1987-2016, room/mod.rs:3793-3822}`
- **Detail:**
  1. **Always-forget leave vs unconfirmed `DeclineInvite`:** `manage::leave()` (`src/matrix/manage.rs:527-540`) always calls `room.leave()` followed by `room.forget()` (deleting local room state and event cache, and vacuuming SQLite), ignoring `forget()` failures with only `tracing::warn!`. Conversely, `Action::DeclineInvite` (`src/app.rs:1495-1504`, invite banner / palette `"Decline invite"`) runs `MatrixCmd::Leave` on **one click/Enter** with no confirmation and without `forget()`.
  2. **`get_dm_room` misses invited & left DMs (`src/matrix/manage.rs:478`):** `client.get_dm_room(&user)` inspects only `joined_rooms()`, so an already-existing *invited* DM causes a duplicate DM creation, and a DM where the peer already left can still be returned as "existing".

Missing `m.room.power_levels` fails `details()` (`line 685`) via `room.power_levels().await` instead of `power_levels_or_default().await` (note: client-side `can_*`/`removable` flags themselves do not introduce privilege escalation because homeserver permissions remain authoritative and errors trigger an `Info` refresh).
  4. **`set_notify` leaks raw SDK error (`src/matrix/manage.rs:571-577`):** Unlike other mutations using `failed(...)` -> `explain()`, `set_notify` sends `truncate(&sanitize_line(&err.to_string()), SERVER_TEXT)` directly to the UI.
